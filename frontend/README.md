# Фронтенд кредитного кабинета

Каркас по [задаче #11](https://github.com/sb1nala/alfa-hack/issues/11): Vite,
React 18, TypeScript в strict-режиме, React Router, TanStack Query и MUI.
Кабинет клиента (#13) работает с настоящим backend: вход, список заявок, подбор продукта, анкета с автозаполнением по ИНН и страница статуса. Кабинет аналитика (#44) — очередь, карточка заявки и форма решения; работает, когда backend реализует API аналитика (B12).

## Запуск в Docker (#15)

Весь стенд, включая фронтенд, поднимается из корня репозитория одной командой; адрес — http://localhost:8080.

```sh
docker compose up -d --build
```

- **Образ:** сборка на `node:24.19.0-bookworm-slim` (`pnpm build` с проверкой типов API), раздача — `nginxinc/nginx-unprivileged:1.27.5-alpine` от непривилегированного пользователя.
- **nginx** (`nginx.conf`): статика SPA с fallback на `index.html`, `/api` → `http://backend:8000` без буферизации (под SSE), загрузка файлов до 10 МБ, заголовки `nosniff`, `DENY`, `same-origin`.
- **Один origin:** браузер видит фронтенд и API на `http://localhost:8080`, поэтому `AUTH_ALLOWED_ORIGIN` по умолчанию равен этому адресу (порт меняется через `FRONTEND_PORT`).
- **Контексты сборки:** compose передаёт `docs/` и `seed/` как `additional_contexts` — приложение берёт из них тексты интерфейса и лимиты продуктов.

## Запуск для разработки

Node.js 24 (проверено на 24.19.0, версия в `.node-version`), pnpm 11.25.0
(версия в `package.json`). Из корня репозитория:

```sh
cd frontend
pnpm install --frozen-lockfile
pnpm dev
```

Откройте http://localhost:5173. Для входа нужен backend, а `AUTH_ALLOWED_ORIGIN` в `.env` должен совпадать с адресом dev-сервера (`http://localhost:5173`).
Корневой адрес перенаправляет на `/client`; неизвестный адрес показывает 404.
Переключение разделов и прямое открытие/обновление страницы работают через Router.
Занятый порт 5173 вызывает явную ошибку вместо запуска на другом порту.

```sh
pnpm typecheck
pnpm build
pnpm preview
```

`build` проверяет типы и создаёт `dist/`. Preview доступен на порту 4173.
Установка воспроизводится по `pnpm-lock.yaml`; `node_modules/` и `dist/` игнорируются.

Переменная описана в `.env.example` и доступна только Vite, секреты не нужны.

## Экраны клиента (#13)

Маршруты и тексты — по `docs/product/screen-map.md` (экраны 1–5) и `docs/product/ui-texts.ru.json`.

| Маршрут | Экран | API |
| --- | --- | --- |
| `/login` | Вход, после него — кабинет своей роли | `auth/csrf`, `auth/login`, `auth/me` |
| `/client` | Мои заявки | `GET /api/applications` |
| `/client/new` | «Для чего деньги»: цель → продукты в порядке `purposes.<code>.products` → черновик | `GET /api/products`, `POST /api/applications` |
| `/client/applications/:id/edit` | Анкета: ИНН → автозаполнение по ЕГРЮЛ (или ручной ввод), сумма, срок, выручка, ориентировочный платёж | `GET /api/companies/lookup`, `PATCH`, `POST .../submit` |
| `/client/applications/:id` | Таймлайн из 6 шагов, карточка статуса, итог решения, отзыв заявки | `GET /api/applications/{id}`, `POST .../cancel` |

- **Роли:** `RequireRole` пускает только нужную роль; без сессии — на `/login`, чужая роль — в свой кабинет.
- **Live-статус:** пока на backend нет SSE (B09), статус опрашивается — раз в 2 с, пока заявку обрабатывает система, раз в 5 с, пока ждём аналитика или клиента, и не опрашивается в конечных статусах. Если `CHECKING` дольше 10 с, показывается `statuses.CHECKING.slow`.
- **Кнопки** определяются `allowed_actions`, а не статусом.
- **Анкета:** границы суммы и срока проверяются при вводе по `seed/products.json`; обязательные поля — при сохранении и отправке. `field_errors` сервера показываются у своих полей. Повторная отправка защищена `Idempotency-Key`.
- **Решение (#14, экраны 6–7):** блок решения на странице заявки, кнопки — по `allowed_actions`.
  - `APPROVED` / `COUNTER_OFFER` — условия; у контрпредложения две колонки «Вы запрашивали / Мы предлагаем» и «Почему условия изменились». «Принять» → `POST accept-offer` → подписание; «Отказаться» → подтверждение `decision.declineConfirm` → `POST cancel`.
  - `NEEDS_INFO` — по каждому пункту загрузка файла (PDF/JPG/PNG до 10 МБ, `POST documents`) или поле выручки; «Отправить данные» → `POST additional-info`. Перед каждым запросом берётся актуальная ревизия: загрузка меняет её.
  - `REJECTED` — причина и «что можно сделать», кнопка новой заявки.
  - `/client/applications/:id/sign` — условия, образец договора, согласие, «Подписать» → `POST sign` (симуляция).
  - Пока backend отдаёт 501 на эти действия (B11), экраны показывают «Эта функция ещё не реализована на сервере». Все тела запросов проверены на Prism по `docs/openapi.yaml`.
- **Логика** (форматирование денег, контрольные цифры ИНН, свёртка статусов в шаги таймлайна, аннуитет) — в `src/lib/`, тесты: `pnpm test`.

## Кабинет аналитика (#44)

Экраны 8–9 `docs/product/screen-map.md`, роль `underwriter`, тексты — `bank.*` в `ui-texts.ru.json`.

| Маршрут | Экран | API |
| --- | --- | --- |
| `/bank` | Очередь: по умолчанию `MANUAL_REVIEW`, переключатель «Все заявки» для демо; обновление раз в 10 с | `GET /api/underwriter/applications` |
| `/bank/applications/:id` | Анкета, скоринг (факторы и вклад), история решений, рекомендация системы, форма решения | `GET /api/underwriter/applications/{id}` |

- **Форма решения:** четыре исхода из `MANUAL_REVIEW`. Одобрение и контрпредложение — продукт, сумма, срок, ставка (пусто — «сообщим при подписании»); контрпредложение — причины из `counterOfferReasons`; запрос данных — документы из `requiredDocuments`; отказ — причина из `rejectionReasons`. Текст для клиента подставляется из словаря и редактируется; «Основание решения» обязательно. Тело запроса собирает `src/lib/bankDecision.ts` (`POST .../decision`).
- **Ограничения контракта:** очередь отдаёт только компанию, статус и время; в карточке нет сырых ответов БКИ/ЕГРЮЛ/ФНС и отдельных полей балла и класса. Балл считается как сумма вкладов факторов, класс читается из аналитического объяснения («Класс D …») — когда `BankDecision` получит `score`/`risk_class`, нужно читать их.
- **Пока API аналитика не реализовано** (501), экраны показывают «Эта функция ещё не реализована на сервере». Проверено на Prism по `docs/openapi.yaml`: тела решений «отказ» и «одобрение с условиями» проходят валидацию контракта.

его не редактируем; суммы остаются строками, статусы и роли — union-типами,


### Переключение Prism ↔ backend одной переменной

Создайте `frontend/.env` по `.env.example`. Меняется только `API_PROXY_TARGET`:

| Сервис | Значение |
| --- | --- |
| Настоящий backend | `http://127.0.0.1:8000` (по умолчанию) |
| Prism | `http://127.0.0.1:4010` |

После изменения перезапустите `pnpm dev`. Переменная не содержит `/api`, учётных
данных или секретов, не имеет префикса `VITE_` и не попадает в браузерный bundle.
Браузер всегда обращается к относительным путям `/api/...` своего origin через
экспортированный `api` из `src/api/index.ts`.

Для работы с Prism:

```sh
# Терминал 1, frontend/
pnpm mock:api
# Терминал 2, frontend/.env содержит API_PROXY_TARGET=http://127.0.0.1:4010
pnpm dev
```

Prism возвращает статические примеры OpenAPI: подходит для разработки запросов
и экранов, но не сохраняет заявки, не реализует настоящий вход, переходы статусов
или SSE. Не следует принимать пример ответа за результат бизнес-процесса.
`pnpm test:prism` поднимает собственные серверы на свободных портах и завершает
их после проверки. Для моделирования cookie в Node используются только
синтетические значения — это не проверка настоящей авторизации.

При работе с настоящим API бэкенду требуется
`AUTH_ALLOWED_ORIGIN=http://127.0.0.1:5173` для приведённого адреса dev-сервера.
Origin включает порт и должен совпадать **точно**. Настройку применяет владелец
backend и перезапускает его. Для локального HTTP также требуется
`AUTH_COOKIE_SECURE=false`. `changeOrigin: false` сохраняет Origin браузера;
CORS и ручной заголовок Authorization не нужны.

Dev-прокси относится к `pnpm dev` и к локальному preview Vite. В production
адрес задаст nginx в задаче #15; менять адрес API в исходниках клиента не нужно.

### Использование

```ts
import { api, ApiError } from './api';

const { data } = await api.http.GET('/api/products');
const { data: application } = await api.http.GET('/api/applications/{application_id}', {
  params: { path: { application_id: applicationId } },
  signal: abortController.signal,
});
if (!application) throw new Error('Карточка заявки не получена');

try {
  const user = await api.auth.login({ login, password });
  // user.role: 'client' | 'underwriter'. Пароль и JWT в ответе отсутствуют.
} catch (error) {
  if (error instanceof ApiError) {
    // Ориентироваться на error.code/status; fieldErrors содержат ошибки формы.
    // requestId можно показать для обращения в поддержку.
  }
}

// Idempotency-Key создаётся один раз на явную попытку отправки и сохраняется
// при ручном повторе той же попытки; expected_revision берётся из свежей карточки.
await api.http.POST('/api/applications/{application_id}/submit', {
  params: { path: { application_id: applicationId }, header: { 'Idempotency-Key': attemptKey } },
  body: { expected_revision: application.revision, consent_to_checks: true },
});
```

`http` типизирует **все** пути контракта и поддерживает GET/POST/PATCH,
параметры, JSON, заголовки, AbortSignal и `parseAs: 'blob'` для скачивания.
`uploadDocument` из `src/api/documents.ts` преобразует `File`, `document_type`
и `expected_revision` в FormData; boundary устанавливается браузером.

### Сессия и ошибки

- JWT читает и отправляет браузер через HttpOnly cookie. Клиент не обращается к
  `document.cookie`, localStorage/sessionStorage и не сохраняет пароли.
- CSRF хранится в памяти экземпляра клиента. Перед мутацией автоматически
  выполняется bootstrap; параллельные мутации делят один запрос токена.
- После успешного login/logout токен очищается и запрашивается заново. После
  `401/403` он очищается; следующий явный запрос может восстановить контекст.
- `ApiError` содержит HTTP status, серверный code, fieldErrors и requestId.
  `ApiNetworkError` означает сетевой сбой; `AbortError` сохраняет смысл отмены.
  Ошибки HTML от прокси не показываются как текст сообщения.
- Автоматических повторов мутаций и перенаправлений нет. `401`, конфликт
  ревизии `409` и бизнес-заглушка `501` обрабатываются будущими экранами #13/#14.
  TanStack Query уже настроен не повторять мутации; `queryFn` может использовать
  тот же клиент и передавать signal.
- Типы проверяют контракт на этапе сборки, а не валидируют каждый успешный JSON
  в runtime. Валидация ответа CSRF и формы серверной ошибки реализована отдельно.

Новые зависимости закреплены в `package.json`/lock-файле и перечислены в
`THIRD_PARTY_NOTICES.md`. Установочная телеметрия транзитивного `@scarf/scarf`
не запускается (точечное `allowBuilds: false` в `pnpm-workspace.yaml`).

### Live-обновления карточки клиента

Экран `/client/applications/:id` подключает нативный `EventSource` к
`/api/applications/:id/events` с cookie того же origin. Четыре именованных
события перечитывают карточку, не подменяя её содержимым SSE. На каждом `open`,
включая переподключение, перечитывается также вся публичная история с пагинацией.
История сохраняется в Query cache; отдельного экрана истории пока нет.

При здоровом соединении опрос карточки выключен. При сбое показывается
`errors.liveUpdatesLost`, повторные GET выполняются раз в 3 секунды.
Нативный reconnect сохраняет `Last-Event-ID`; источник в состоянии `CLOSED`
пересоздаётся после успешного чтения API. Ответы с меньшей `revision` не
перезаписывают свежие данные. При `401/403/404`, уходе со страницы, конечном
статусе и выходе источник закрывается, запросы отменяются; `401` также
перепроверяет сессию. Экраны действий и банковская очередь сохраняют свой опрос.

Проверка на полном стенде: открыть карточку отправленной заявки, наблюдать
статусы без перезагрузки, остановить и восстановить backend, проверить
предупреждение и получение пропущенного статуса. В Network должен оставаться
один `/events`, а после ухода или выхода — ни одного. На Prism доступен
первоначальный снимок; настоящий поток предоставляет backend B09.
