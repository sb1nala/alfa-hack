# Интеграционная проверка восстановления React UI

`scripts/check_ui_browser.cjs` после основного UI-сценария вызывает
`frontend/scripts/check-docker-recovery.cjs`. Существующая задача CI
«Clean Docker product» запускает его на исходном Docker Compose-стенде.
Workflow, API, backend и зависимости не меняются.

Первый реальный прогон обнаружил, что при Offline браузера существующий EventSource
может оставаться OPEN, поэтому его `error` не сообщает об отключении сети.
Контроллер React теперь также слушает `offline/online`: показывает потерю связи,
приостанавливает обновления до Online и перечитывает карточку с историей при возврате
сети. Существующий нативный источник сохраняется; при остановке контроллера сетевые
обработчики удаляются. Добавлен регрессионный unit-тест этого случая.

Проверяются четыре случая: Offline/Online браузера, Offline с явно закрытым
нативным EventSource, остановка/запуск backend с настоящим 502 nginx,
пересоздание контейнера backend с восстановлением через Docker DNS nginx.
При 502 Chromium может сохранять CONNECTING; тест не предполагает, что каждый
502 обязательно даёт CLOSED. Для отдельного терминального случая тест вызывает
настоящий `EventSource.close()` во время Offline, затем возвращает Online.
Данные и HTTP/SSE-ответы не подменяются; это явная инъекция сбоя браузерного транспорта.

Для каждого случая через React создаётся новая заявка `demo-manual`.
В отдельном банковском браузерном контексте сотрудник открывает карточку,
видит `review_reason` и принимает решение кнопкой интерфейса. Во время Offline
решение принимается, пока клиент не имеет сети. После возврата сети клиент
получает решение и действия без перезагрузки. Во время 502 видна сохранённая
карточка; попытка отзыва даёт ошибку и не повторяется автоматически.

Проверяются один активный EventSource, перечитывание истории самим React,
совпадение банковского решения с клиентской карточкой, реальный сохранённый
переход APPROVED в истории, отсутствие внутренних причин в публичном решении,
закрытие потока и отсутствие отложенного переподключения после выхода.
EventSource только наблюдается обёрткой; запросы и ответы не подменяются.

Команды остановки затрагивают только backend проекта `alfa-b10-<случайный hex>`,
созданного существующим оркестратором. Передаются его точные Compose-аргументы
и приватное окружение; стандартный проект разработчика не используется.

Повторение на машине с Docker, Python и Playwright/Chromium:

```sh
python3 scripts/check_product_docker.py
```

Настройка `PLAYWRIGHT_MODULE` и `CHROMIUM_EXECUTABLE` — как у существующего
`scripts/check_sse_browser.cjs`. В CI это уже настроено. Для проверки используется
приватный конфиг оркестратора; в отчёт не попадают его содержимое и учётные данные.
Результат каждого случая печатается строкой `PASS React Docker recovery`,
а итоговая таблица добавляется в GitHub Actions job summary.

Локальный прогон с фикстурой из `QA-RECOVERY.md` остаётся отдельной быстрой проверкой.
Фактический результат Docker-прогона и точный SHA указываются в PR и Actions run;
само наличие этого скрипта не считается успешной приёмкой.
