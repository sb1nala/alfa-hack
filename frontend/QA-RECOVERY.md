# Проверка восстановления React UI — 24.10.2026

База: `main` на `baa4cec067f73b525795291c756a544e03297fc6`.
Проверена production-сборка Vite в headless Chrome (Playwright 1.62.1).
Компоненты React, маршрутизация, TanStack Query, fetch и браузерный EventSource настоящие.
API заменён локальным HTTP/SSE-стендом на синтетических примерах `docs/openapi.yaml`:
он управляет ответами 502, разрывами потока, снимками заявки и страницами истории.
Обёртка EventSource только записывает экземпляры и `readyState`, не заменяет транспорт.

## Результат

Все 10 сценариев прошли. В каждом сценарии загружен ровно один HTML-документ;
React не падает с необработанными исключениями.

| Сценарий | Проверено |
| --- | --- |
| Отключение сети браузера | Плашка о потере связи, сохранённая карточка, после возврата сети — новое решение и действия без перезагрузки |
| Штатный CONNECTING | Используется тот же EventSource; Chromium отправляет Last-Event-ID; решение обновляется |

Во всех сценариях восстановления после нового снимка перечитываются обе страницы

На проверенных страницах при 375 и 1280 px нет горизонтального переполнения документа.
Скриншоты очереди, карточки, кода и дополнения данных просмотрены вручную.

## Как повторить

Из `frontend/`, Node согласно `.node-version`:

```sh
pnpm build
pnpm test:recovery
```

Для запуска нужен установленный Playwright с Chromium. Новых зависимостей в
продукт не добавлено: используется тот же внешний браузерный инструмент, что и
в `.github/workflows/ci.yml`. Если он установлен отдельно, задайте `PLAYWRIGHT_MODULE`
как абсолютный путь к пакету Playwright. `CHROMIUM_EXECUTABLE` позволяет использовать
установленный Chrome вместо загруженного Chromium. `QA_OUTPUT` задаёт папку отчёта.
По умолчанию JSON и PNG сохраняются в `frontend/coverage/recovery/` (игнорируется Git).
Ошибка завершает команду с ненулевым кодом; отчёт содержит имя упавшего сценария.
Проверка запускается отдельно: в существующий CI чужой зоны ответственности она не добавлена.

## Что остаётся общей QA-приёмке

Этот прогон подтверждает поведение рабочего React UI при управляемых сбоях,
но не проверяет реальный FastAPI/worker/PostgreSQL, nginx/Docker DNS, содержимое
истории из БД и сохранение решений/документов в БД. Локально Docker недоступен.
Банковское решение и отправка файла здесь проверяются до HTTP-запроса и ответа фикстуры;
это не доказательство обработки документа или решения настоящим backend.

Для окончательной приёмки повторить на чистом Docker-стенде текущего `main`:

1. Создать синтетическую заявку `demo-manual`, открыть карточку клиента. В DevTools
   включить Offline; во второй, банковской сессии принять решение. Вернуть Online:
   клиент получает решение и действия без reload, плашка исчезает.
2. Остановить backend при открытой карточке. Проверить 502, плашку и сохранение карточки.
   Действие во время сбоя показывает ошибку. Зафиксировать CLOSED, если браузер в него
   переходит; вернуть backend, затем принять решение аналитиком. Проверить восстановление,
   ровно один поток, перечитывание истории и отсутствие повторной отправки действия.
3. Проверить разрыв и штатный reconnect, Last-Event-ID, уход со страницы и выход из
   учётной записи. Просроченную сессию проверять отдельно от временного сбоя связи.
4. Повторить основные сценарии решения, загрузки и подписания на backend; записать
   точный SHA, браузер, результаты и артефакты для продукта/QA.

`review_reason` уже подключён в #93, банковские подписи статусов — в #95.
Общая QA-приёмка этим отчётом не закрывается.
