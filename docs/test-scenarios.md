# Тест-сценарии

Владелец: Продукт/QA · задача #27 · данные: [`test-data.md`](test-data.md) (политика `2026-10-22.draft2`)

Сценарии проверяют прототип так, как его будет проверять жюри: в браузере и через API на чистом `docker compose up`. Каждый сценарий привязан к синтетической компании из `seed/companies.json` и к запросам коллекции Bruno из [`api-collection/`](../api-collection/).

## Подготовка

1. Запустить стенд с нуля:

   ```bash
   docker compose down -v && docker compose up --build --wait
   ```

2. Дождаться, пока все сервисы станут `healthy` (`--wait` делает это сам). Кабинет: <http://localhost:8080>, Swagger: <http://localhost:8000/docs>.
3. Браузер: кабинет клиента и кабинет аналитика открыть в двух разных окнах (например, обычном и приватном), чтобы видеть обе стороны одновременно.
4. API: открыть папку `api-collection/` в [Bruno](https://www.usebruno.com/) и выбрать окружение по логину компании (`demo-approve`, `demo-term`, …). Подробнее — в [README коллекции](../api-collection/README.md).

Тестовые аккаунты: клиенты — логины `demo-*`, пароль `demo-2026`; аналитик — `analyst` / `analyst-2026`.

## TS-06. Ручная проверка аналитиком

**Компания:** ООО «СтройМонтаж», ИНН `0085481212` · клиент `demo-manual`, аналитик `analyst`.

1. **Клиент** подаёт заявку: кредитная линия, 8 000 000 ₽, 24 мес.
2. **Ожидаем `MANUAL_REVIEW`.** Клиент видит «Заявку изучает специалист», кнопок решения нет.
3. **Аналитик** входит (02 Аналитик / 01–04) и видит заявку в очереди «Заявки на ручную проверку» (запрос 05).
4. В карточке (запрос 06) видны:
   - анкета;
   - внешние проверки: просрочка 45 дней, 6 запросов в БКИ;
   - класс риска D (65 баллов);
   - факторы с вкладом;
   - рекомендация системы `gray_zone`.
5. Аналитик выбирает решение (один из запросов 07–10), указывает причину для клиента и основание решения.
6. **Ожидаем:** в окне клиента статус сменился без перезагрузки. В истории заявки (TS-11) решение записано с автором-аналитиком.
7. Если решение — «Запросить данные» без основания решения, кнопка «Вынести решение» не отправляет форму и подсвечивает поле.

Для демо по умолчанию выбираем `COUNTER_OFFER` на 5 млн ₽ / 24 мес.

1. Подать заявку: экспресс-кредит, 1 000 000 ₽, 12 мес.

## TS-09. Сбой БКИ и повтор

**Компания:** ИП Соколов Д. А., ИНН `005849901413` · `demo-bki`. Мок БКИ отвечает `503` на первые 2 запроса.

1. Перед проверкой перезапустить мок, чтобы сбросить счётчик сбоев: `docker compose restart mocks`.
2. Подать заявку: экспресс-кредит, 1 500 000 ₽, 24 мес.
3. **Ожидаем:** заявка держится в `CHECKING` дольше обычного. Через ~10 с клиент видит «Один из источников отвечает дольше обычного. Мы повторяем запрос автоматически — заявка не потеряется».
4. В логах worker видны 2 неудачные попытки и третья успешная:

   ```bash
   docker compose logs worker
   ```

5. **Ожидаем `APPROVED`** (класс A, 170 баллов). Заявка не ушла в ошибку, ничего не пришлось нажимать.
6. **Дополнительно:** остановить мок на время проверки (`docker compose stop mocks`), убедиться, что кабинет клиента продолжает работать, затем запустить его снова (`docker compose start mocks`). Заявка должна продолжить обработку.

## TS-10. Live-статус без перезагрузки

1. Во время любого сценария (TS-01, TS-06) **не обновлять страницу**: статус, таймлайн и блок решения меняются сами.
2. Проверка через API. Cookie `access_token` берётся из браузера (DevTools → Application → Cookies):

   ```bash
   curl -N --cookie "access_token=<токен>" http://localhost:8000/api/applications/<id>/events
   ```

   Ожидаем поток событий `status_changed` и `decision_created`.
3. Разорвать соединение (на минуту выключить сеть в DevTools). Должна появиться плашка «Обновления статуса временно не приходят. Мы переподключаемся автоматически». После восстановления сети статус догоняется.

## TS-11. Аудит переходов

1. После TS-01 открыть «История заявки» (запрос 10).
2. **Ожидаем:** по событию на каждый переход статуса (`DRAFT` → `SUBMITTED` → `CHECKING` → `SCORING` → `APPROVED` → `OFFER_ACCEPTED` → `SIGNED` → `ISSUED`) с временем и инициатором (клиент, система, аналитик).
3. После TS-06 в истории есть решение аналитика с основанием. Основание видно только в кабинете банка, клиенту — нет.

## TS-13. Запуск с нуля

На машине, где проект не разрабатывали:

1. Клонировать репозиторий, скопировать `.env.example` в `.env`, вписать `AUTH_JWT_SECRET` (команда генерации — в README).
2. Запустить `docker compose up --build --wait`.
3. **Ожидаем:**
   - db, backend, mocks и frontend в статусе `healthy`, worker запущен;
   - одноразовый сервис `migrate` завершился с кодом 0: миграции применены, 10 аккаунтов, 9 компаний и 4 продукта загружены;
   - кабинет открывается по адресу из README;
   - проходит TS-01.
4. Время от команды до работающего кабинета записать в журнал прогонов.
